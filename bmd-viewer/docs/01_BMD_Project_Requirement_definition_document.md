# BMD Viewer 프로젝트 요구사항 정의서

문서 버전: 1.0
작성일: 2026-06-25
프로젝트명: BMD Viewer (X-ray 기반 골밀도 측정·추적 시스템)

---

## 1. 프로젝트 개요

### 1.1 목적
2D X-ray(DICOM) 영상으로부터 요추 L4 척추의 골밀도(BMD, Bone Mineral Density)를 측정하고, 환자별로 누적된 측정값의 변화를 추적하여 의사가 골다공증 진행 상황을 판단할 수 있도록 지원하는 임상 보조 도구를 개발한다.

### 1.2 핵심 가치
측정 결과의 정확성과 함께, 의사가 모델의 판단을 신뢰할 수 있도록 설명가능 인공지능(XAI)을 통해 골밀도 값에 영향을 준 항목을 함께 제시한다.

### 1.3 사용자 및 대상
시스템 사용자는 의사(및 영상의학 전문의)이며, 측정 대상은 환자다. 의사는 자신이 담당하는 환자의 X-ray를 업로드하고 분석 결과를 확인한다.

### 1.4 범위
본 프로젝트는 환자 관리, DICOM 업로드, 비동기 추론(척추 분할 + L4 BMD 산출 + XAI), 측정 이력 조회, 골밀도 추세 시각화를 포함한다. 추론 모델 자체의 학습은 별도 작업(기존 노트북 파이프라인)에서 수행하며, 본 시스템은 학습된 모델을 서비스에 통합한다.

### 1.5 비범위 (이번 단계 제외)
PACS 연동, 다기관 데이터 공유, 청구/보험 연동, 모바일 전용 앱은 이번 범위에 포함하지 않는다.

## 2. 기술 스택 및 아키텍처

### 2.1 기술 스택
백엔드는 FastAPI와 SQLite(비동기 SQLAlchemy)로 개발하며, 추론은 업로드 후 비동기 작업으로 처리한다. 프론트엔드는 React(Vite) + TypeScript로 개발하고 데이터는 초기에는 REST(SQLite 백엔드)를 사용하되 추후 Firebase로 교체할 수 있도록 데이터 계층을 추상화한다. 배포는 백엔드/프론트엔드 각각의 Docker 이미지와 docker-compose로 구성하여 임의의 클라우드에 올릴 수 있도록 한다.

### 2.2 아키텍처 원칙
다른 프로젝트에 통합하거나 일부를 재사용할 수 있도록 다음 원칙을 따른다.

첫째, 추론 엔진은 인터페이스(`BmdInferenceEngine`)로 분리하여, 기존 노트북의 척추체 추출 및 BMD 계산 로직을 해당 인터페이스의 구현으로 이식하기만 하면 나머지 코드 변경 없이 동작하도록 한다.

둘째, 프론트엔드의 데이터 접근은 `DataProvider` 인터페이스를 통해서만 이뤄지며, SQLite(REST) 구현을 Firebase 구현으로 교체해도 화면 컴포넌트는 변경하지 않는다.

셋째, 기능은 feature 단위(`patients`, `xray`, `bmd`, `auth`)로 분리하여 폴더째 다른 프로젝트로 이식할 수 있게 한다.

넷째, 데이터베이스는 연결 URL만 교체하면 SQLite에서 PostgreSQL 등으로 전환할 수 있도록 구성한다.

### 2.3 데이터 흐름
의사가 DICOM을 업로드하면 서버는 파일을 저장하고 즉시 202(Accepted)를 반환한 뒤, 백그라운드에서 추론을 실행한다. 추론이 완료되면 측정 결과가 저장되고, 프론트엔드는 처리 상태를 폴링하여 완료 시 결과를 표시한다.

## 3. 도메인 모델

시스템의 핵심 엔티티와 관계는 다음과 같다.

의사(Doctor)는 여러 환자(Patient)를 담당한다. 환자는 여러 건의 X-ray 스터디(XrayStudy)를 가진다. 각 스터디는 하나의 BMD 측정 결과(BmdMeasurement)를 가진다. 측정 결과는 여러 개의 추출된 척추 분할(VertebraSegment)과 여러 개의 XAI 기여 항목(XaiFactor)을 가진다.

| 엔티티 | 주요 속성 | 설명 |
|--------|-----------|------|
| Doctor | email, full_name, role | 시스템 사용자(의사). 역할 구분 보유 |
| Patient | medical_record_no, full_name, sex, birth_date | 환자. MRN과 이름으로 검색 |
| XrayStudy | dicom_path, status, acquired_at | 업로드된 X-ray 1건과 처리 상태 |
| BmdMeasurement | bmd_value, t_score, confidence | L4 기준 추론 결과 |
| VertebraSegment | label, is_target, bbox | 추출된 척추(L1~L5), L4 식별 |
| XaiFactor | label, contribution, description | BMD에 영향을 준 항목과 기여도 |

## 5. 비기능 요구사항

### 5.1 성능
DICOM 업로드 응답은 추론 완료를 기다리지 않고 즉시 반환(202)되어야 한다. 환자 목록 검색은 일반적인 규모에서 1초 이내로 응답해야 한다.

### 5.2 보안 및 개인정보
환자 정보는 의료 개인정보로 취급한다. 모든 API는 인증된 의사만 접근할 수 있으며, 의사는 자신이 담당하는 환자의 데이터에만 접근할 수 있다. 비밀번호는 bcrypt로 해싱하여 저장한다. 운영 환경에서는 비밀키와 토큰 만료시간을 환경변수로 안전하게 주입한다.

### 5.3 이식성 및 확장성
데이터베이스, 추론 엔진, 프론트엔드 데이터 계층은 각각 교체 가능한 경계를 가진다. 단일 노드의 비동기 처리(BackgroundTasks)는 부하 증가 시 큐 기반(Celery 등)으로 전환할 수 있도록 워커 인터페이스를 분리한다.

### 5.4 배포
백엔드와 프론트엔드는 각각 Docker 이미지로 빌드되며, docker-compose로 통합 실행한다. 스토리지(DICOM/파생 산출물)는 볼륨으로 분리하여 컨테이너 재시작 시에도 유지한다.

### 5.5 안전성 고지
본 시스템이 산출하는 BMD 값은 X-ray 기반의 proxy(대리) 추정치이며, 의료기기로 승인된 DXA 측정을 대체하지 않는다. 화면과 문서에 본 한계를 명시하고, 최종 판단은 의사의 임상적 판단에 따른다는 점을 분명히 한다.
